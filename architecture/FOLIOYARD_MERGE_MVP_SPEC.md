# Folioyard architecture and Merge PDF MVP

**Status:** Architecture documented before product implementation.  
**Research date:** 2026-10-12.  
**Repository state:** The selected workspace contains brand-preview assets but no application source, package manifest, or Git repository. The preview remains reference material only.

## Product boundary

Build a single focused Merge PDF workbench. A person can select/drop two or more PDFs, see the ordered source list, reorder sources using keyboard-accessible controls, inspect a real page preview, merge in that order, preview the generated file, and download it. Source PDFs remain unchanged.

No accounts, server upload, document persistence, telemetry, or arbitrary document-count cap are needed for this first tool. Memory availability, browser limits, PDF complexity, and file size remain physical constraints; the UI should state a real constraint when encountered rather than inventing a quota.

## Sources checked

- [PDF.js project and Apache-2.0 license](https://mozilla.github.io/pdf.js/) and [current browser setup guide](https://mozilla.github.io/pdf.js/getting_started/): PDF parsing/rendering has a display API and a separate worker; worker use requires a served app rather than `file://`.
- [pdf-lib project and MIT license](https://github.com/Hopding/pdf-lib), [PDFDocument API](https://pdf-lib.js.org/docs/api/classes/pdfdocument), and [encryption/limitations notes](https://github.com/Hopding/pdf-lib#encryption-handling): page-copy API is `copyPages`; encrypted PDFs are unsupported; `ignoreEncryption` does not decrypt and is explicitly discouraged. Document copying is not guaranteed to retain every catalog-level structure (the API warns that acroforms/outlines are not copied by `copy()`).
- Package registry metadata checked on 2026-10-12 with `npm view`: `pdf-lib` 1.17.1 (MIT), `pdfjs-dist` 6.4.299 (Apache-2.0), React 19.3.0 (MIT), Vite 8.3.4 (MIT; Node `^20.19.0 || >=22.12.0`), TypeScript 7.0.2 (Apache-2.0), Vitest 5.0.4 (MIT). The scaffold and lockfile now pin these versions.
- [PDF24/iLovePDF/Smallpdf/Adobe/PDFgear public sources](../research/COMPETITOR_COMPARISON_MATRIX.md) informed interaction and privacy decisions; the research file distinguishes observations from vendor claims.

## Implementation implications

- Use **PDF.js (`pdfjs-dist`) only for reading/rendering** and **pdf-lib only for structural merge**. Do not make one library carry the viewer, editor, encryption, and conversion surface.
- Put structural merge in a dedicated Web Worker so a large file does not freeze the React UI. PDF.js uses a separate worker for parsing; keep its worker asset explicitly wired and verify it in a production build. Do not assume canvas painting is off the main thread unless the selected PDF.js API and supported browsers demonstrate that path.
- Keep files as `File` references in tab memory. Read fresh `ArrayBuffer`s for preview and merge rather than transferring the same buffer that a renderer may consume. Do not put document bytes in IndexedDB, localStorage, analytics, logs, or URL state.
- The worker loads one source at a time, copies pages in source order with `copyPages`, and reports completed files/pages. Progress is indeterminate during a single large parse; do not display a fabricated percentage. A cancel action terminates the owned worker and keeps the source queue so the person can retry or remove a problematic file.
- On success, reload the generated bytes with PDF.js for a real output preview; compare output page count to the sum of input page counts before enabling download. The result name is `folioyard-merged.pdf`. Revoke prior output object URLs on replacement and component teardown.
- No worker or browser path sends files over the network. Do not add third-party fonts, analytics, cloud connectors, or remote APIs to this milestone. A local browser's normal request for the app shell/worker is not a file upload.

## System shape

```text
React workbench
  ├─ source queue and accessible reorder controls
  ├─ PDF.js preview component ── PDF.js parsing worker
  └─ Merge controller ───────── Dedicated merge Web Worker
                                 └─ pdf-lib: load → copyPages → save
                                      ↓ bytes + verified page count
                                PDF.js output preview → browser download
```

### Small module boundaries

- `src/App.tsx`: owns selected `File`s, source order, active source/page, merge state, error, and output.
- `src/PdfPreview.tsx`: renders the active page from PDF.js; cancels stale render tasks and releases its loading task/canvas on replacement.
- `src/merge.worker.ts`: loads sequentially, copies pages, saves output, posts typed progress/result/error messages. It never reads UI state or contacts a server.
- `src/merge.ts`: pure merge function shared by worker and unit tests; no DOM dependency. It reports page totals from source documents and returns bytes.
- `src/pdfjs.ts`: wires PDF.js to its separately bundled parsing worker; production packaging is build-verified.
- `tests/merge.test.ts`: generated synthetic fixtures for page ordering, multipage, rotations, invalid data, and encrypted input; no private user PDFs.

## Interaction and states

1. Initial state: a restrained title and one clear `Add PDFs` control with a full-width drop target. A short local-processing statement is factual only after the network test confirms it.
2. Queue state: source names, real byte sizes, real page counts, and sequence position in a compact list separated by rules. Each row has `Move up`, `Move down`, and `Remove` buttons. Disable only impossible moves. No drag-only requirement and no decorative metrics.
3. Preview: render the selected source one page at a time with previous/next page controls, page count, and a readable page canvas. On narrow viewports keep controls touch-sized and the active document visible.
4. Merge: enabled only with at least two valid inputs. The original queue stays visible. Worker messages name the current file and completed-file count. `Cancel` terminates the worker and returns to an editable queue.
5. Failure: show a specific message inline and associate it with the affected row; retain all source files for recovery. Invalid/corrupt files remain removable. Encrypted inputs get a clear unsupported message; do not ask for a password or try to bypass encryption.
6. Success: only after the output reopens and its page count equals the input-page sum, show output page count/size, render the merged file in the preview, and enable `Download merged PDF`. If output validation fails, do not offer a download.
7. Cleanup: clear file references and revoke URLs when the user removes sources, resets the tool, or closes the page. Browser refresh intentionally clears the in-memory session.

## Error and PDF support contract

- Accept input based on successful parsing, not MIME type alone; browser MIME types can be absent or wrong.
- **Encrypted/password-protected:** reject with a direct explanation. `pdf-lib` 1.17.1 does not support encrypted PDFs, and `ignoreEncryption` does not decrypt them. The encrypted fixture test verifies this failure path.
- **Malformed or non-PDF bytes:** reject without losing the remaining queue. Do not silently omit a source.
- **Multipage and rotated pages:** preserve page order, dimensions, and page rotation; cover these properties in tests and verify the merged output in PDF.js.
- **Metadata, forms, signatures, bookmarks, links, attachments, layers, and unusual PDF features:** do not promise universal fidelity from the first merge. Page copying can omit document-level structures; digital signatures cannot remain valid after the bytes are modified. Before claiming support for complex interactive PDFs, add representative fixtures and evaluate a different merge engine if pdf-lib changes page behavior or loses needed structures.
- **Memory:** browser workers improve responsiveness but do not remove memory cost. Each PDF must be parsed, output bytes held for preview/download, and pages copied. Avoid unnecessary duplicate arrays, process documents sequentially, catch allocation failures, preserve the queue, and tell the user to try fewer/smaller files if the browser reports resource exhaustion. Do not impose a synthetic count/size quota.

## Acceptance criteria and test plan

- Two valid one-page files produce a valid, downloadable PDF with two pages in the selected order.
- A multipage source contributes all pages in order; output page count equals the exact input sum.
- A rotated source page retains its rotation and renders in the output preview with the intended orientation.
- A non-PDF/corrupt fixture shows an error, produces no output, and leaves other source files recoverable.
- An encrypted fixture fails with the explicit unsupported message; no password is requested and no encrypted output is generated.
- Keyboard reorder buttons change actual merge order; boundaries are correctly disabled. A one-step `Undo` restores the previous source order. Remove/add recovers from bad input.
- Worker progress corresponds to real file completion; cancellation leaves the queue editable and cannot later replace the output with a stale result.
- The downloaded bytes reopen in PDF.js and pass structural assertions; the browser download name is correct.
- Network capture during selection, preview, merge, and download shows no document bytes sent to external or same-origin endpoints; the app makes no analytics or telemetry calls.
- Responsive browser screenshots show the implemented desktop and mobile workbench, with no horizontal overflow, clipped controls, or fake states. Use the Drive quality gate's named viewport set for QA; save at least desktop 1440px and mobile 390px screenshots in the deliverables.
- Run tests, typecheck, production build, keyboard pass, and browser verification. Do not claim pass until each command/check is run.

## Deferred from this milestone

Split, compression, conversion, signing, annotation, rotation, page-level rearrangement, cloud integrations, OCR, batch export, accounts, and telemetry. The MVP only reorders whole source PDFs. These tools require separate feature contracts, library evaluations, tests, and accurate limits.
